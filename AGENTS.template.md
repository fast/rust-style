## Rust Style

- **Modules and imports**: Order module headers as `//!` docs, `use` imports (`group_imports = "StdExternalCrate"`, `imports_granularity = "Item"`), out-of-line `mod` declarations, and items. Use `<module>/mod.rs` for multi-file modules, and do not split cohesive files prematurely. Group `mod` declarations with blank lines between `pub mod`, private `mod` with immediate `pub use self::...;` re-exports, and implementation-only private `mod` (`#[cfg(test)]` last), sorted alphabetically within each group; re-export subsystem interfaces from `mod.rs` and attach `#[cfg]` gates at module boundaries when possible. Import symbols at the top of the file from `crate::...` (avoiding `super::...` and private `self::...`, reserving `use super::*;` for `#[cfg(test)]` modules), preserve original names with meaningful module or crate qualification (such as `io::Error`, `fs::read`, or `ptr::read_unaligned`), and avoid `use ... as ...` aliases except `use ...::Trait as _;` (inline paths are fine for collisions such as `core::error::Error` or rare hooks such as `std::panic::catch_unwind`).
- **Visibility**: Use three visibility tiers: private by default, plain `pub` inside private ancestor module trees, and `pub(crate)` for internal fields, constructors, or helpers reachable through `pub mod` or `pub use` re-exported types. Avoid `pub(super)` and `pub(in ...)`, and never widen visibility solely for cross-module tests.
- **Types, traits, and lints**: Name items by concrete role, keep a type and its primary `impl` together (public API before private helpers), and reserve `len` and `is_empty` for collection or slice-like views. Use `new` (with `Default` when parameterless and `const fn` when trivial), `with_*` for alternative required inputs, and `*Builder` for multi-option construction. Do not prefix struct fields with `_` to silence warnings; keep descriptive names and add `#[expect(dead_code, reason = "...")]` on unread ownership or guard fields. Omit `PartialEq` and `Eq` when field equality would expose internal layout or history, avoid unnecessary generic bounds on custom `Debug` impls, reserve `#[must_use = "..."]` for lazy values or `&self` methods easily mistaken for mutators, and use `#[expect(..., reason = "...")]` instead of `#[allow(...)]`.
- **Control flow and errors**: Keep abstractions at signatures, cohesive types, and module boundaries; inside functions, prefer linear control flow with guard returns, explicit `match` or `if let`, and explicit `for` loops for multi-step or fallible logic over premature helpers or uncontracted defensive glue. Use `Result` (keeping failing mutations atomic when practical) for recoverable errors, empty values or `Option` for absent queries, fail-fast panics for broken invariants, and structured error context rather than string parsing.

## Documentation

- Document caller-observable contracts in `///` comments without leaking implementation details. Use noun phrases for types, third-person present-tense verbs for operations, and public API labels on intra-doc links (`` [`Codec`][crate::compress::Codec] ``).
- Include `# Errors`, `# Panics`, `# Safety`, and trailing `# Examples` (with visible imports) only when applicable, explaining simple return values in the summary or body.
- Reserve `//` comments for non-obvious invariants, `// SAFETY:` preconditions, or external quirks rather than restating code.

## Testing

- Exercise observable contracts through public APIs and keep `#[cfg(test)]` unit tests next to the implementation strictly for private invariants that black-box tests cannot reach.
- Every test must guard a realistic regression without mirroring literals, trivial control flow, static type guarantees, or non-contract `Debug` wording.
- Avoid test-only production hooks, and coordinate concurrent tests deterministically instead of sleeping.
